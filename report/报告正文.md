# 一、需求与目标

本课程项目要求围绕真实需求构建一个可运行、可评估、可复现的 Agent。本项目选择“垃圾短消息审核”作为任务场景：课程群、社团群或短信收件箱中经常出现广告引流、中奖诈骗、贷款推销等垃圾消息，管理员若逐条人工阅读，不仅耗时，而且容易在消息量大时漏判。Agent 的价值在于先做一遍自动判别，把高把握的结果直接处理，把没把握的结果交给人工，并用相似历史消息帮助人工快速复核。

目标用户是课程群/社区群的管理员以及普通收件人。现有做法是人工阅读后删除或忽略，缺点是重复劳动多、标准不统一、夜间或高峰期响应慢。本项目要改善的是“单条短消息的垃圾判别与处置建议”：输入一条消息文本，输出标签、置信度、处理动作和相似历史消息。项目范围限定为文本二分类，不处理图片、语音和链接跳转后的网页内容，也不做自动删除数据库记录等高影响操作。

成功标准设置如下，数值以真实测试集结果为准：主模型 Macro-F1 不低于 0.95，垃圾类 F1 不低于 0.90，系统对空输入等异常不崩溃，并且能够触发低置信度转人工分支。实际结果中，主模型 Macro-F1 为 0.9705，垃圾类 F1 为 0.9482，三个演示输入均正常返回，其中一条低置信度消息成功转入人工复核，达到预设目标。

评估样例来自公开数据集 UCI SMS Spam Collection[5][6]。该数据集含 5574 条带标签短信，项目去除 414 条完全重复短信后保留 5160 条，按 80/20 分层随机划分，测试集 1032 条，随机种子 42。选择公开数据集而不是自行编造样例，是为了保证实验可核查、可复现；数据集的英文短信属性作为已知局限在讨论部分说明。

# 二、方案与系统设计

Agent 的任务入口十分明确：用户提供一条短消息文本；Agent 返回 JSON，包含 `label`（`spam` 或 `normal`）、`confidence`、`action`（`通过` / `隐藏` / `转人工复核`）、`reason` 和 `similar_comments`。任务成功的判定方式是：在测试集上分类指标达标，并且在演示中能正确走完“输入—处理—输出”全流程。

Agent 工作流分为六步。第一步，输入校验，拒绝空输入和超过 500 字的超长输入；第二步，文本分词，把连续文本切成词序列；第三步，向量化，把文本变成模型能计算的数字特征；第四步，朴素贝叶斯分类，输出标签和概率；第五步，置信度闸门，概率低于 0.65 时不自动处置，转人工复核；第六步，相似消息检索，用 TF-IDF 余弦相似度从本地消息库找 Top3 相似文本，为人工判断提供对照。每一步都在代码中有独立函数，便于解释和调试。

系统连接的数据源是本地 `data/comments.csv`，由公开数据集转换而来；检索组件基于 scikit-learn 的 TF-IDF 与线性核。所有工具都在本地运行，不调用外部大模型 API，也不上传用户消息，避免隐私外泄。对“高影响结果”的处理采取保守策略：即便模型给出高置信度，系统也只输出建议，不直接执行删除或封禁；低置信度则强制转人工。

备选方案有两个。其一是做一个通用聊天界面，让大模型自由回答，但这无法定义明确成功标准，也不满足课程对机器学习方法的要求，因此放弃。其二是直接调用大模型 API 做分类，但新版评分标准明确指出“单纯调用通用大模型 API 不足以满足机器学习组件要求”，因此本项目坚持自己完成数据处理、特征构造、模型训练与评估。

异常处理覆盖五类情况：输入为空、输入过长、数据文件缺失、数据标签不足两类、检索工具或数据源失败。前两类返回友好错误；后三类在启动或调用时报出明确原因，不输出不可靠结果，也不假装工具调用成功。这样既保证演示稳定，也符合评分标准对“失败与安全处理”的要求。

# 三、机器学习方法

数据处理环节读取 UCI 原始文件，按第一个制表符切分标签和正文，把 `ham` 映射为 `normal`、`spam` 映射为 `spam`，合并连续空白并去掉首尾空白，再去掉完全重复的短信。去重是必要的：如果不去重，同一条短信可能同时出现在训练集和测试集，指标会虚高。处理后数据规模为 5160 条，其中正常消息 4518 条，垃圾消息 642 条，垃圾类占比约 12.4%。因此本项目不只看准确率，还报告垃圾类的 Precision、Recall 和 F1。

特征表示比较了词袋模型和 TF-IDF。词袋模型只统计词在消息中出现的次数，好比把一袋棋子倒出来数每种颜色有几个，不关心顺序；TF-IDF 在词频基础上考虑逆文档频率，给“只在少数消息中出现的词”更高权重。朴素贝叶斯[1]根据先验概率和条件概率计算后验概率，适合文本分类这种高维稀疏场景。代码中设置 `alpha=1.0` 作拉普拉斯平滑，防止测试集中出现训练时没见过的词导致概率为 0。

训练与推理使用 scikit-learn[2][3] 的 `Pipeline`，把向量化器和分类器串成一条流水线。这样做的好处是训练与预测使用完全相同的处理步骤，避免“训练时分词、预测时不分词”的低级错误。向量化器只在训练集上拟合，测试集不参与训练，杜绝数据泄漏。数据划分采用分层随机抽样，保证训练集和测试集的类别比例接近原始分布。

基线包括多数类基线，即永远预测出现最多的 `normal`。这个基线准确率有 0.8760，但 Macro-F1 只有 0.4669，垃圾类 F1 为 0，说明单看准确率会被类别不平衡误导。主模型最终选择“词袋 + 朴素贝叶斯（有 jieba 分词）”，因为它在真实测试集上 Macro-F1 达到 0.9705，垃圾类 F1 达到 0.9482，均优于 TF-IDF 对照模型。这一选择是**根据实验结果做出的事后调整**，不是事先指定；报告如实记录了调整过程。

机器学习组件在 Agent 中的作用是提供“判别结果 + 置信度”。没有模型，Agent 只剩规则匹配；有了模型，Agent 才能对未见过的消息做概率判断，并把置信度交给闸门决定是否转人工。因此模型不是装饰，而是 Agent 决策链的上游核心。

# 四、Skills 与组件复用

本项目复用组件清单如下。jieba[4] 版本 0.42.1，MIT 许可证，来源 https://github.com/fxsjy/jieba ，用途是中文分词；scikit-learn[2][3] 版本 1.9.1，BSD-3-Clause 许可证，来源 https://scikit-learn.org/ ，用途是向量化、朴素贝叶斯、指标计算和数据划分；Python 3.13.12 标准库提供 csv、json、argparse 等基础能力；UCI SMS Spam Collection[5][6] 数据集版本为 2011 年发布版，DOI 10.24432/C5CC84，CC BY 4.0 许可证，用途是训练与测试。以上版本均由 `pip list` 与官方页面核对，不凭记忆填写。

深入分析 jieba。它解决的子任务是中文分词：中文没有空格，计算机不知道“加微信领资料”该切成几个词，jieba 把连续汉字切成词序列。它的输入是字符串，输出是词列表，例如 `jieba.lcut("加微信wx12345领内部资料")` 得到 `["加", "微信", "wx12345", "领", "内部", "资料"]`。它主要依赖本地词典，不调用外部服务，不需要网络权限。局限在于网络新词、缩写和错别字容易切错，不同领域常需要自定义词典。

本项目的核验方式有三步。第一，阅读项目 README，确认 `jieba.lcut()` 的返回类型。第二，在终端试跑英文样例 `jieba.lcut("Free entry in 2 a wkly comp to win FA Cup")`，得到按词切分的结果，确认它对英文短信也能工作。第三，在真实数据上做消融实验：TF-IDF 组内，有分词时 Macro-F1 为 0.8586，关掉 jieba 改成单字切分后为 0.9309。这个结果是**反直觉的**：分词并没有提升效果。原因分析是本项目使用英文短信数据，jieba 的中文词典优势无法发挥；这属于组件与任务语言不匹配，而不是“分词一定有害”。报告不隐瞒这一结果，并据此提出改进方向。

集成适配工作包括：编写 `make_tokenizer(use_jieba)` 让分词可以一键开关，便于消融；把分词函数接入 sklearn 流水线，保证训练与预测一致；过滤空白词；在分词前做输入校验；把 jieba 缓存目录指向项目内 `.tmp/`，解决本机临时目录权限问题。自己编写的部分包括 Agent 流程、置信度闸门、异常处理、相似检索、实验编排、数据转换脚本和报告分析；复用部分均已标注来源，不把复用写成自研。

# 五、实验设计与结果

测试集构造已在第一节说明：UCI 公开数据，5574 条原始短信，去重 414 条，最终 5160 条；其中正常消息 4518 条，垃圾消息 642 条；80/20 分层划分，训练集 4128 条，测试集 1032 条，随机种子 42。筛选规则是去掉完全重复项与空行，不改动短信正文；数据来自公开研究语料，无需额外采集个人通信内容，因此没有引入新的隐私信息。

评价指标包括准确率、Macro-F1、垃圾类 Precision / Recall / F1 和混淆矩阵。真实测试集上的结果如下表所示，完整混淆矩阵见 `experiments/demo_results.md`。

| 模型 | 准确率 | Macro-F1 | 垃圾类 P | 垃圾类 R | 垃圾类 F1 |
| --- | --- | --- | --- | --- | --- |
| 基线1：多数类 | 0.8760 | 0.4669 | 0.0000 | 0.0000 | 0.0000 |
| 主模型：词袋+NB（有分词） | 0.9874 | 0.9705 | 0.9675 | 0.9297 | 0.9482 |
| 对照：TF-IDF+NB（有分词） | 0.9496 | 0.8586 | 1.0000 | 0.5938 | 0.7451 |
| 消融：TF-IDF+NB（无分词） | 0.9719 | 0.9309 | 0.9541 | 0.8125 | 0.8776 |

主模型的混淆矩阵为：真实 normal 中 900 条判对、4 条误判为 spam；真实 spam 中 119 条判对、9 条漏判为 normal。对照模型 TF-IDF+NB 的垃圾类漏判达到 52 条，明显高于主模型，这也是最终选择词袋模型的重要依据。

对照实验说明主模型选择有据。多数类基线虽然准确率不低，但完全不会识别垃圾类，证明准确率单独使用会误导。词袋+NB 在 Macro-F1 和垃圾类 F1 上均明显优于 TF-IDF+NB，因此部署采用词袋模型。消融实验在 TF-IDF 组内进行，去掉 jieba 后 Macro-F1 从 0.8586 升到 0.9309，说明在英文短信数据上，单字切分反而保留了更多有用子串特征；这与中文直觉不同，但正是真实实验的价值所在。

失败案例一是一条安全提醒：“Please protect yourself from e-threats. SIB never asks for sensitive information like Passwords, ATM/SMS PIN thru email. Never share your password with anybody.” 真实标签是正常，模型以 0.8697 置信度判为垃圾。原因是词袋模型看到了 `Passwords`、`PIN`、`sensitive information`、`Never share` 等在诈骗短信中常见的词，却没有理解 `never asks` 的否定结构。这属于特征表示与语义上下文不足，改进方向是加入否定短语特征或补充安全提醒类正常样本。

失败案例二是一条带电话号码的短消息：“Sorry I missed your call let's talk when you have the time. I'm on 07090201529”。真实标签是垃圾，模型以 1.0000 置信度判为正常。这条短信表面像私人约聊，文本里没有典型广告词；数据集把它标为垃圾，可能依赖号码的历史行为，而这些上下文不在文本中。因此这是数据标注依赖外部信息、任务边界模糊造成的错误，而不是分词问题。模型过度自信说明高置信度并不等于正确，系统不应把高置信度结果直接用于高影响操作。

完整运行过程在 `experiments/demo_run.md`。其中垃圾广告样例被判为 `spam`、置信度 1.0、动作“隐藏”；正常聊天样例被判为 `normal`、置信度 1.0、动作“通过”；低置信度样例 “Nokia phone is lovly..” 被判为 `spam` 但置信度仅 0.523，低于阈值 0.65，Agent 输出“转人工复核”。这三条演示覆盖了成功处置和人工兜底两条路径，终端截图与完整 JSON 输出见演示材料，可作为报告截图依据。

# 六、讨论与改进

从真实使用价值看，主模型垃圾类 F1 为 0.9482，说明在公开基准上 Agent 能显著减少人工阅读量；低置信度转人工机制又避免了模型独自承担风险。但必须承认，数据集是英文短信，而课程群常见的是中文评论，两者在语言、长度和广告形式上均有差异，因此系统不能直接当成中文社区审核工具上线。这是本项目最重要的边界。

风险方面，误报会把正常消息当成垃圾，代价是打扰用户；漏报会让广告或诈骗消息留在群里。阈值 0.65 的设定是为了在两者之间取折中：低于该值不自动处置。但失败案例二显示，高置信度也可能出错，因此报告明确提出：对含可疑电话号码、短链接等强风险特征的消息，即使置信度高也应增加规则复核，而不应完全信任模型。

有证据支持的改进是：既然消融实验显示当前英文数据上 jieba 未带来收益，下一步应换成真实中文垃圾评论数据集，并重新运行开/关分词的消融实验，验证 jieba 在语言匹配后是否能提升 Macro-F1。这个改进直接来自本项目的实验结果，而不是空想。另一个改进是针对失败案例一加入否定短语特征，减少把安全提醒误判为诈骗。

仍未解决的问题包括：词袋和 TF-IDF 都不理解上下文和语义，无法处理反讽、变体字和新词；模型依赖标注数据，垃圾类占比低时召回率容易波动；数据集标签可能依赖文本外的号码历史，单靠文本无法完全复现人工判断。这些问题需要在后续工作中通过更大规模中文数据、上下文模型和规则复核共同解决。
